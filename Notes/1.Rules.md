# LFM AI Project Guide

This document combines the project overview, development rules, and current configuration TODOs for **LFM (Linux File Manager)** into one organized reference for AI-assisted development.

---

# 1. Project Overview

## What LFM is

LFM (Linux File Manager) is a **Linux-only file manager** intended to replace other Linux file managers such as Nautilus and Nemo.

## Product direction

LFM is not just a UI concept. It is a **desktop application** built with:

- **Vue** for the user interface
- **Tauri** for the desktop runtime and system integration
- **TypeScript** for all application code
- A Linux-first design mindset

The project should remain focused on a practical, polished, and maintainable desktop file manager experience.

# 3. Vue, Frontend, and UI Rules

## Vue architecture

1. Use the **Composition API** only.
2. Do not use the Options API.
3. Prefer reusable composables and utilities over duplicated logic.
4. Split large components into smaller ones when readability or maintenance starts to suffer.
5. Avoid deeply nested logic.
6. Prefer early returns and simple conditions.
7. Prefer computed properties instead of repeating logic in templates.
8. Do not place business logic directly inside Vue templates.
9. Use meaningful, descriptive names for variables, functions, files, and components.
10. Avoid inline styles in templates.
11. Keep styles scoped unless global styling is required.

## Templates and styling

1. Use **Pug** for Vue templates.
2. Do not use raw HTML templates when Pug is expected.
3. In Pug files, keep attributes on a single line unless the line becomes unreadable.
4. Use **Sass (`.sass`)** for component styles when styles are needed. and use @apply inside it to write tailwindcss.
5. Keep the component structure in this order:

```vue
<script setup lang="ts"></script>
<template lang="pug">
div(class="section")
</template>
<style lang="sass" scoped>
// Needed so @apply/tailwindcss can work
@reference "tailwindcss"
div.section
 @apply w-full h-full bg-(--bg-default)
</style>
```

1. `@reference "tailwindcss";` is needed in style so `@apply` can work.
2. Use Tailwind and DaisyUI conventions where appropriate.
3. Use DaisyUI themes from `src/styles/vendor/daisyui.css`.
4. Support both light and dark mode with DaisyUI.
5. Keep the frontend visually polished and functional, not just decorative.

## UI and component organization

1. Use the `LFM` prefix for CSS class names to avoid naming conflicts.
2. Place reusable UI components inside a shared `components/` directory.
3. Keep UI logic, business logic, and API logic separate.
4. Keep the project very organized and categorized.
5. Use semantic and accessible UI elements whenever possible.
6. Use absolute imports or aliases instead of long relative paths.
7. Avoid hardcoded values when a constant or configuration file is more appropriate.
8. Keep code readable and maintainable over being clever.

# 4. TypeScript and State Management Rules

## TypeScript

1. Use strict typing for all data structures.
2. Prefer interfaces and well-defined types.
3. Do not use `any` unless absolutely necessary.
4. Keep type definitions in dedicated `types/` files when they are reused.
5. Prefer native TypeScript features before adding more dependencies.

## State and data flow

1. Use Pinia for state management.
2. Use the latest stable Pinia patterns with state, getters, and actions.
3. Prefer composables for shared behavior.
4. Avoid unnecessary reactivity in Vue.
5. Use VueUse where it improves developer experience or code clarity.
6. Use constants and shared configuration for repeatable values.
